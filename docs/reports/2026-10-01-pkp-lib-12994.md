# After an upgrade from 3.5, reviewers cannot accept or decline a review request when the journal asks about competing interests

- **Severity** high
- **Effort** small
- **Kind** regression
- **Crash** server
- **Affects**
  - main: OJS, OMP (OMP by code; its upgraded schema walked)
  - 3.5: none (code; the column and its writers are `main` only)
  - 3.4: none (code)
  - 3.3: none (code)
- **Introduced** `pkp/pkp-lib#13073` for `pkp/pkp-lib#12994` · [07b19290b4](https://github.com/pkp/pkp-lib/commit/07b19290b4) · 2026-07-23 · Jarda Kotěšovec (jardakotesovec)
- **Upstream** fix in PR `pkp/ojs#5688` (open, not yet in main), covering OJS only; nothing found for OMP or OPS (2026-10-01)
- **Tracked in** ci-triage "Open regressions" · Temporary: delete once acted on
- **Checked** 2026-10-01, each branch's tip (the commits in Evidence)

## Summary

On a journal or press upgraded from 3.5 to `main`, once a manager has
written the reviewers' "Competing Interests" guidance, the server fails
whenever a reviewer answers a request: "Accept Review, Continue to Step
#2" leaves the reviewer on step 1, and "Decline Review Request" leaves
the window open, with nothing on screen and the request unchanged. An
editor's "Modify Review" of a completed review fails the same way and
shows the raw database error in the window. A fresh install of `main`
works; only upgraded sites meet it, every one of them that asks the
competing-interests question.

## Impact

- **Lost**: the review itself. A reviewer cannot accept or decline, so
  no review can start on an upgraded site that asks the question; the
  reviewer is told nothing, and the editor sees only an unanswered
  request. An editor's correction of a completed review is not saved.
- **Who**: every reviewer and editor on every journal or press upgraded
  from 3.5 whose Settings › Workflow › Review › "Reviewer Guidance" has
  a "Competing Interests" text (a common setup; the dataset's journal
  has none until a manager writes it). Not a preprint server, which has
  no review.
- **Way round**: none on screen. Removing the guidance text lets
  reviewers answer, at the cost of the question the journal wants asked.

High: a core task, reviewing, fails with no way round on every
upgraded site that asks about competing interests; it would be critical
if the default setup asked the question.

## Steps to reproduce

Preconditions:
- The default dataset, OJS `stable-3_5_0` (3.5.0.5), upgraded to OJS
  `main` with `php tools/upgrade.php upgrade`.

1. Sign in as `dbarnes`. Open Settings › Workflow › "Review" ›
   "Reviewer Guidance", type "Reviewers declare any relationship with
   the authors." into "Competing Interests" and press "Save". Sign out.
2. Sign in as `jjanssen` and open the review request for "Sodium
   butyrate improves growth performance of weaned piglets during the
   first period after weaning".
3. Leave "I do not have any competing interests" selected, tick the
   privacy consent box and press "Accept Review, Continue to Step #2".
4. Sign out, sign in as `phudson` and open the same submission's review
   request.
5. Press "Decline Review Request", keep the message and press "Decline
   Review Request" in the window.

**Expected.** At step 3 the request opens on step 2, "Guidelines"; at
step 5 the window closes and the request is declined, as on a fresh
install of `main` and on 3.5.

**Observed.** At step 3 the page stays on step 1 with no message; at
step 5 the window stays open with no message. Both requests are still
unanswered. The server log:

```
[500]: POST /index.php/publicknowledge/en/reviewer/saveStep/12?step=1 - Uncaught PDOException: SQLSTATE[42703]: Undefined column: 7 ERROR:  column "competing_interests_declared" of relation "review_assignments" does not exist
[500]: POST /index.php/publicknowledge/en/reviewer/saveDeclineReview/12 - Uncaught PDOException: SQLSTATE[42703]: Undefined column: 7 ERROR:  column "competing_interests_declared" of relation "review_assignments" does not exist
```

Without step 1 (no guidance text) a reviewer accepts as expected.

## Cause

pkp-lib `07b19290b4` (`pkp/pkp-lib#13073`, for `pkp/pkp-lib#12994`)
records whether a reviewer answered the competing-interests question in
a new column, `review_assignments.competing_interests_declared`. It adds
the column to the install migration (`ReviewsMigration`) and ships the
upgrade migration
`classes/migration/upgrade/v3_6_0/I12994_CompetingInterestsDeclared.php`,
but no app lists that migration in its `dbscripts/xml/upgrade.xml`, so
`tools/upgrade.php` never runs it. The OJS half, `pkp/ojs#5688`, which
adds the line, is still open; OMP and OPS have no such change.

The review assignment DAO maps `competingInterestsDeclared` to the
column (`classes/submission/reviewAssignment/DAO.php` line 51), and
`EntityDAO` writes every mapped property the object holds, so any save
that sets it issues an `UPDATE … competing_interests_declared = …`,
which PostgreSQL refuses. Three writers set it, all when the context has
competing-interests guidance or the request carries an answer:
`PKPReviewerReviewStep1Form::execute()` (accepting),
`PKPReviewerHandler::saveDeclineReview()` (declining), and
`ReviewAssignmentController` (the editor's "Modify Review", `PUT
…/reviewAssignments/{id}/review`). Reads do not fail: a missing column
is skipped and the declaration reads false.

Reach: the same `upgrade.xml` gap is in OMP (walked: its upgraded
dataset lacks the column; the reviewer flow is the shared code) and OPS
(the column is missing, but a preprint server has no review, so nothing
reaches it). The back-fill the migration does (a stored statement marks
the review as declared) is skipped too, so a 3.5 review's statement is
not shown as a declaration on the `main`-only open-review page and peer
review API (read in the code, not walked: the dataset holds no
statement).

## Proposed fix

List the migration in each app's `dbscripts/xml/upgrade.xml`, in the
3.6.0 block after the last pkp-lib migration (the way every other
`v3_6_0` migration is registered):

```diff
 		<migration class="PKP\migration\upgrade\v3_6_0\I12813_UpdateAuthorResponseAndSubmissionCommentTextType"/>
+		<migration class="PKP\migration\upgrade\v3_6_0\I12994_CompetingInterestsDeclared"/>
 		<code function="rebuildSearchIndex" />
```

as [fix-ojs.diff](../../shared/playwright/checks/sync/upgrade-3_5/fix-ojs.diff),
[fix-omp.diff](../../shared/playwright/checks/sync/upgrade-3_5/fix-omp.diff) and
[fix-ops.diff](../../shared/playwright/checks/sync/upgrade-3_5/fix-ops.diff).
`pkp/ojs#5688` does this for OJS at an older position in the list; OMP
and OPS need the same line. The migration already guards with
`Schema::hasColumn()`, so installs that ran it by hand (the issue names
the `tools/migration.php` command) upgrade cleanly. The alternative, a
guard in the DAO that skips the column when it is missing, would hide
the gap and leave the back-fill undone. Tried: with the line in all
three files, the three upgraded datasets have the column, and the steps above end on step 2 and in a declined
request, with no 500.

The guard: the campaign's dataset fleets now compare an upgraded
dataset's columns with a fresh install's and name every difference; a
schema-parity check after `upgrade.php` in pkp's own CI would catch the
next missing line.

A second, harmless gap the same comparison names: `I11702_ExtendTasks`
(pkp-lib `aff80d393e`, `pkp/pkp-lib#11699`) calls
`$table->removeColumn('status')`, which only edits the Blueprint and
drops nothing, so upgraded sites keep `edit_tasks.status` (filled by
its default, read by nothing; tasks and discussions work). `dropColumn()`
is the call meant, in `up()` and in `down()`.

Small: one line in three files, tried.
