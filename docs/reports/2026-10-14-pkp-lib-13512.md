## Summary

A journal manager uploads a "Logo", "Homepage Image" or journal
thumbnail as a BMP picture, which the upload box accepts, and presses
"Save". The form shows "Saved", but nothing is stored. If the journal
already had a logo, it disappears from every public page, and the
header shows the journal's name as text. The same happens with a
journal style sheet whose opening lines PHP's file-type check
misreads, such as the one in the Steps, which opens with a comment
block and a `:root` rule. The journal's earlier style sheet stops
loading on every page.

Nothing on screen says the file was refused. The manager sees the loss
only on the public pages, or as an empty box after reloading the
settings. Uploading a PNG, JPEG, GIF or WebP picture works. A CSS file
can be rewritten until it is accepted, but nothing says that is what
to do.

The change behind this is meant to refuse a non-image uploaded as the
favicon or logo, such as an HTML file, and the fix proposed here keeps
that refusal. But the change also refuses picture types the box offers
and real style sheets, which the issue never mentions, and it wipes
the value the setting held.

## Impact

- **Lost**: the journal's logo, homepage image, thumbnail or custom
  style sheet, on every public page, from the moment of the save. The
  old file stays on the server but nothing refers to it. No one is
  told.
- **Who**: a journal manager (or press or server manager) on Settings ›
  Website › "Appearance", with a BMP picture (or AVIF, TIFF or HEIC,
  which the box also offers), or a CSS file the server's type check
  misreads. Most managers use PNG or JPEG. About 3 in 100 of the
  non-empty CSS files in the apps' code and bundled libraries are
  misread.
- **Way round**: save the picture as PNG or JPEG and upload it again.
  For a style sheet, change its opening lines until it is accepted.

Medium: it takes a narrow input, but the save looks done and silently
removes a public logo or style sheet the journal already had. It would
be high if common exported theme CSS were misread as often as the
files the apps ship.

## Cause

`PKPContextService::moveTemporaryFile()` (lib/pkp
`classes/services/PKPContextService.php`) picks the extension a
context file is stored under. Before `266505ecd8`, a type that neither
list knew got no extension, and the file was stored anyway:

```php
$extension = $publicFileManager->getDocumentExtension($temporaryFile->getFileType());
if (!$extension) {
    $extension = $publicFileManager->getImageExtension($temporaryFile->getFileType());
}
$fileName .= $extension;
```

After it, an image setting takes its extension from
`getImageExtension()` alone, and any setting whose type neither list
knows is refused:

```php
$extension = $publicFileManager->getDocumentExtension($temporaryFile->getFileType());
if (!$extension || $isImage) {
    $extension = $publicFileManager->getImageExtension($temporaryFile->getFileType());
    if (!$extension) return false;
}
```

The refusal happens after validation, inside the save. `_saveFileParam()`
returns `false` when the move refuses. `edit()` stores that `false` over
the setting's value without checking it, and the save answers 200, so
the form says "Saved". Each app's `ContextService::afterEditContext()`
does the same for its thumbnail (`setData()` of the result). The commit
meant to refuse a non-image uploaded as the favicon or logo. It does,
but at a point where it can neither report the refusal nor keep the
previous value.

Two neighbours decide which files reach that refusal:

- `getImageExtension()` (lib/pkp `classes/file/FileManager.php`) knows
  GIF, JPEG, PNG, WebP and the icon types (and some Flash, audio and
  video types), but not BMP, AVIF, TIFF, HEIC or SVG. The "Logo", "Homepage Image"
  and thumbnail boxes are `FieldUploadImage` with the default
  `acceptedFiles: 'image/*'`, so they let BMP, AVIF, TIFF, HEIC and SVG
  through. "Favicon" sets its own list (`image/x-icon,image/png,image/gif`),
  all of which the server takes.
- A style sheet's type comes from PHP's `finfo`, corrected by
  `PKPString::getAmbiguousExtensionsMap()`, which turns only
  `css:text/plain` and `css:text/x-c` into `text/css`. A CSS file read
  as `text/x-asm`, `text/troff`, `text/x-algol68` or (empty)
  `application/x-empty` keeps that type and is now refused.

Reach:
- Logo, homepage image and style sheet: walked on screen, OJS `main` and
  3.5. Favicon: the same `edit()` path, read in the code. Its box
  refuses other types first, so only the REST API reaches it.
- The app thumbnails: walked through the settings route the form uses
  (OJS `journalThumbnail` became `[]`). OMP and OPS were read in the
  code (`pressThumbnail`, `serverThumbnail`, the same hook).
- `PKPContextService::add()`: the same `_saveFileParam()` call, read in
  the code.
- Unchanged, read in the code: the publication cover image
  (`PKP\publication\Repository::_saveFileParam()` checks the image type
  first and calls the move without `$isImage`), the category image, and
  the site's logo and style sheet (`PKPSiteService`, its own copy).

## Proposed fix

A proposal, tried on OJS `main`; the team decides. Refuse the file in
the API's validation step, where the form can show why, and never store
a refusal over the setting. The diff is
[fix.diff](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-13512/fix.diff)
for pkp-lib, applied at the app root.
[fix-ojs.diff](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-13512/fix-ojs.diff)
is the same plus OJS's thumbnail.

- **One rule, used twice.** A new
  `PKPContextService::getFileExtension(TemporaryFile, bool $isImage)`
  holds the rule `266505ecd8` added, unchanged. `moveTemporaryFile()` calls it,
  and so does a new `validate()` check placed beside
  `ValidatorFactory::temporaryFilesExist()`. For "Logo", "Homepage
  Image" and "Favicon" (per language) and for the style sheet, a
  temporary file the rule refuses becomes a field error: the existing
  `form.invalidImage` ("An invalid image was uploaded. Accepted formats
  are .png, .gif, or .jpg.") for pictures, and a new
  `manager.setup.styleSheet.invalid` ("The file could not be read as a
  style sheet. Please upload a CSS file.") for the style sheet. The
  save answers 400, the form shows the message under the box, and
  nothing changes. This follows `PKP\category\Repository::validate()`,
  which refuses a category image of the wrong type with
  `form.invalidImage` in the same way.
- **A refused move keeps the old value.** `edit()` restores the
  setting's current value when `_saveFileParam()` returns `false`.
  Each app's `afterEditContext()` does the same for its thumbnail,
  reading it from `$currentContext`. Each app's `validateContext()`
  adds the type check for the thumbnail beside OJS's existing "file
  exists" check (OPS has the same check; OMP checks nothing there
  today). OJS's lines are in `fix-ojs.diff`; OMP and OPS need the
  same lines, not written or tried here.
- **The box offers what the server takes.** The default
  `FieldUploadImage` `acceptedFiles` becomes
  `image/gif,image/jpeg,image/png,image/webp`, the types
  `getImageExtension()` stores. A BMP is then refused in the box itself
  ("You can't upload files of this type.") before anything is sent.
- **Misread style sheets.** `getAmbiguousExtensionsMap()` gains
  `css:text/x-asm`, `css:text/troff` and `css:text/x-algol68` →
  `text/css`, beside the existing `css:text/plain` and `css:text/x-c`.

```php
// PKPContextService::edit(), after each _saveFileParam() call
if ($params[$fileUploadParam][$localeKey] === false) {
    $params[$fileUploadParam][$localeKey] = $context->getData($fileUploadParam, $localeKey);
}
```

Tried with `fix-ojs.diff` on OJS `main`, on the default dataset loaded
fresh. Steps 4 and 6: the box refuses `logo.bmp` with "You can't upload
files of this type.", and the PNG logo stays in the header. Step 8:
`asm.css` is stored as `styleSheet.css` and the home page turns red.

Neighbour checks, same trial:
- An empty `.css` file answers 400 with the message above under
  "Journal style sheet" and "Please correct one error." at the foot.
  The earlier style sheet stays.
- A BMP sent to the logo and to the journal thumbnail through the
  settings route answers 400 with `form.invalidImage`. Both PNGs stay.

The keep-the-old-value part alone (the validation left out) kept every
earlier value, though "Saved" still showed. A first try that kept the
value inside `_saveFileParam()` stored `{"temporaryFileId":…}` as the
thumbnail, because the app hook passes the context already built from
the request. That is why the guard sits in `edit()` and in the hooks.

**Alternatives**:
- Add BMP and AVIF to `getImageExtension()` instead of narrowing the
  box. That changes what every image upload in the apps takes (covers,
  announcements, highlights), and it is a product call. SVG is a
  separate decision.
- Keep only the old value, with no validation. This stops the wipe, but
  the manager is still told "Saved" for a file that was dropped.
- Revert `266505ecd8`. This loses what the issue asked for.

**What goes with it**:
- REST API: a `PUT contexts/{id}` with a refused file answers 400 with
  the field error, where it now answers 200 and empties the setting.
- Other image boxes that use the default list (the site's logo,
  announcements, highlights, an issue's cover) also narrow to the
  types their servers store. The category image stores only JPEG, PNG
  and GIF (`Category::SUPPORTED_IMAGE_TYPES`), so it can pass its own
  shorter list.
- No data repair. A setting emptied since 2026-10-13 is restored by
  uploading the file again; the old file is still on disk.
- Backport: the same lines on `stable-3_5_0` (`2196fa2775`). The issue
  lists 3.3 and 3.4 as affected, so a backport of the change there
  needs this fix with it.
- Tests: a unit test for `validate()` with a BMP and a `text/x-asm`
  temporary file, and the e2e guard in spec U10 (A21).

Medium: four files in pkp-lib and a few lines in each app's
`ContextService` (two repos at least), one new locale string, and a
behaviour change for every image box that uses the default list.
