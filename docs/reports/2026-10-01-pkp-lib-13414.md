# Importing a users file again after updating adds every ended role a second time, and Editorial History lists the period twice

- **Severity** low
- **Effort** small
- **Kind** regression
- **Affects**
  - main: OJS, OMP (code; the state comes only from a 3.5 install, see Steps)
  - 3.5: OJS, OMP
  - 3.4: none (code; its import keeps no role dates)
  - 3.3: none (code; its import keeps no role dates)
- **Introduced** `pkp/pkp-lib#13414` (main) and `pkp/pkp-lib#13413` (3.5) for `pkp/pkp-lib#13412` · [2e377d27fc](https://github.com/pkp/pkp-lib/commit/2e377d27fc) · 2026-09-30 · Bozana Bokan (bozana)

## Summary

A journal or press that imported a users file with ended roles on a 3.5
release, and imports the same file again after updating, gets each
ended role added a second time, with the "The import completed
successfully." message and no warning. About › "Editorial History" then
lists each such person's period twice ("2026 – 2020, 2018 – 2020").
Before this change the second import added nothing.

## Impact

- **Lost**: nothing; a duplicate role row per ended role, shown on the
  public Editorial History, which a manager has to remove person by
  person. Nobody is told.
- **Who**: managers who re-import a users file (to move people between
  journals, or to repeat an import) whose roles carry end dates, on a
  journal that first imported that file on a 3.5 release from before
  `pkp/pkp-lib#13390` (3.5.0-5 and earlier), on 3.5 after the update and
  on `main` after the upgrade. Files without end dates are not touched.
- **Way round**: remove the duplicate rows on each user's roles page.

Low: a wrong but visible record on a public page, in a rare state (a
re-import of an old file with ended roles); it would be medium if
re-importing such files were routine.

## Steps to reproduce

Preconditions:
- The default dataset, OJS `stable-3_5_0`, on a 3.5 release from before
  `pkp/pkp-lib#13390` (lib/pkp at `d3216eed72`, the state of every 3.5.0
  release up to 3.5.0-5).
- A users file, [legacy.xml](../../shared/playwright/checks/sync/pkp-lib-13412/legacy-reimport.js)
  (the script writes it), with two new users, each holding "Section
  editor" from `2018-01-01 00:00:00` to `2020-01-01 00:00:00` and
  "Reader" with no dates.

1. Sign in as `dbarnes`, open Tools › "Users XML Plugin", upload the
   file and press "Import Users". The results read "The import completed
   successfully. …".
2. Open About › "Editorial History": each user is listed under "Section
   editor" with "2026 – 2020" (the old import stored the import day as
   the start).
3. Update the install to the `stable-3_5_0` tip (or upgrade it to
   `main`).
4. As `dbarnes`, import the same file again on Tools › "Users XML
   Plugin".
5. Reload About › "Editorial History".

**Expected.** Step 4 adds nothing, as importing an app-made file twice
does since `pkp/pkp-lib#13412`, and as the same re-import did before it;
Editorial History still lists one period per user.

**Observed.** Step 4 reads "The import completed successfully. Users with
usernames and email addresses that are not already in use have been
imported, along with accompanying user groups." and each user now holds
"Section editor" twice (`2026-10-01 … – 2020-01-01` and `2018-01-01 –
2020-01-01`). Editorial History reads "Section editor 2026 – 2020, 2018 –
2020" for each.

Control: on lib/pkp `8809a197de` (3.5 with `pkp/pkp-lib#13390`, before
`#13412`), step 4 adds nothing.

## Cause

Before `pkp/pkp-lib#13390` the users import ignored the file's
`<date_start>` and stored the import day, so an ended role from the
file was stored with a start after its end. `#13412` replaced the
"already holds an active or ended row" check with an overlap check in
`UserXmlPKPUserFilter::parseUser()` (`plugins/importexport/users/filter/UserXmlPKPUserFilter.php`,
lines 354–369): an existing row overlaps when it ends after the file's
start and starts before the file's end. A row that starts after its own
end never starts before the file's end, so it is not found, the
"already imported" test never sees it, and the role is created again.
This follows the issue's "no overlap: import" rule; the rows the old
import wrote were not considered.

Reach: OJS and OMP (the shared filter; OPS has no users import). Only
rows with a start after their end; `endAssignments()` and the role
screens never write one (read in the code), so they come from users
imports on 3.5.0 releases alone.

## Proposed fix

Treat a stored row whose start is after its end as a row whose start
is unknown, in the overlap query and in the "already imported" test, in
the shared filter
([fix.diff](../../shared/playwright/checks/sync/pkp-lib-13412/fix.diff)):

```diff
                                         fn (Builder $query) => $query->whereNull('user_user_groups.date_start')
                                             ->orWhere('user_user_groups.date_start', '<', $dateEnd)
+                                            // The import before start dates were kept stored the import day as the start,
+                                            // after an ended role's end: such a row's start is unknown.
+                                            ->orWhereColumn('user_user_groups.date_start', '>', 'user_user_groups.date_end')
 …
-                                    : $existing->dateStart?->toDateTimeString() === $dateStart && $existing->dateEnd?->toDateTimeString() === $dateEnd
+                                    : ($existing->dateStart?->toDateTimeString() === $dateStart || ($existing->dateEnd !== null && $existing->dateStart > $existing->dateEnd))
+                                        && $existing->dateEnd?->toDateTimeString() === $dateEnd
```

This keeps `#13412`'s rules for every well-formed row, and the issue
already treats a missing start the same way ("the export writes it for
roles from before start dates were stored"). The alternative, an
upgrade migration that sets `date_start` to NULL where it is after
`date_end`, would also correct Editorial History's "2026 – 2020" for
those rows, but it changes stored data on every site and needs a 3.5
patch-release migration; it can follow the filter fix. With the fix, a
file whose earlier period overlaps such a row is reported as
overlapping rather than imported, since the row's real start is
unknown.

Tried on 3.5 (the filter is the same file on `main`): with the diff
applied, step 4 adds nothing and Editorial History keeps one period per
user, on OJS and OMP; a file first imported at the tip and imported
again still adds nothing, silently.

Small: two conditions in one method, tried, and a unit test with a
row whose start is after its end.
