# Users & Roles: screen readers announce every user row's "…" button as a raw code

- **Severity** low
- **Effort** small
- **Kind** defect
- **Affects**
  - main: OJS, OMP, OPS
  - 3.5: OJS, OMP, OPS
  - 3.4: none (code; the older user grid, no "…" button)
  - 3.3: none (code; the older user grid, no "…" button)
- **Introduced** `pkp/ui-library#437` for `pkp/pkp-lib#9658` · [e65555cf](https://github.com/pkp/ui-library/commit/e65555cf63f327dcad705eb6aa3bb43150ef7c38) · 2025-02-04 · Ipula Indeewara (ipula)
- **Upstream** `pkp/pkp-lib#12646` (open), reported on OMP 3.5.0
- **Tracked in** spec U53 [A5](https://github.com/jardakotesovec/pkp-e2e/blob/main/docs/specs/U53-users-management.md#a5)
- **Checked** 2026-10-01, each branch's tip (the commits in Evidence)

## Summary

On Settings › Users & Roles, "Users" tab, a screen reader announces the
"…" button at the end of every row as "##userAccess.management.options##"
instead of a word such as "Options"; the menu it opens reads normally.

The manager gets the job done: the button opens the row's menu ("Edit",
"Email", "Remove User", …) and every action works. The code shows because
the button's name points to a text that exists in no language.

`pkp/pkp-lib#12646`, open, reports the same fault on OMP 3.5.0 without a
cause or a fix. This report adds the cause, a one-line fix tried on all
three apps, and OJS, OPS and `main`, so the team can comment there or
close one of the two as a duplicate.

## Impact

- **Lost:** nothing. A screen-reader user hears a code instead of what
  the button does.
- **Who:** managers who use a screen reader, on the Users & Roles list.
  Sighted users see only the "…" icon and are not affected.
- **Way round:** none needed, since the menu's items are named normally.

Low: a raw translation key as a control's name. A higher level would
need a screen-reader user to be unable to tell this button from the
row's other controls. It is the row's only button, so that does not
happen.

## Steps to reproduce

Preconditions:

- PKP's default test dataset for `main` (`publicknowledge`).
- A screen reader (NVDA, VoiceOver), or the browser's developer tools
  with the Accessibility pane, which shows the name a screen reader is
  given.

Steps:

1. Sign in as `rvaca` (the manager).
2. Open Settings › Users & Roles
   (`/index.php/publicknowledge/management/settings/access`). The
   "Users" tab lists "Current Users (39)" (a press "(38)", a preprint
   server "(25)").
3. Click in the search box "Enter a user's name, role (e.g Journal
   editor), or affiliation" and press Tab once. The focus moves to the
   "…" button at the end of the first row, "admin admin".
4. Listen to the name the screen reader announces (or read the button's
   Name in the Accessibility pane).
5. Press Enter. The row's menu opens.

**Expected:** the button is announced by a name that says what it does,
as the "…" buttons of the app's other lists are: a button named "More
Actions". The menu lists the row's actions.

**Observed:** the focused button, as the browser gives it to a screen
reader:

```
role: button   name: "##userAccess.management.options##"
```

All 25 rows on the first page carry that name (its `aria-label`). The
menu reads "Edit", "Email", "Remove User", "Disable User".

The column these buttons sit in has a header only screen readers get,
and it reads "MORE ACTIONS".

## Cause

`UserAccessManagerCellActions.vue` (ui-library,
`src/managers/UserAccessManager/`) renders each row's menu as
`DropdownActions` with `button-variant="ellipsis"` and
`:label="t('userAccess.management.options')"` (line 5). For the ellipsis
variant, `DropdownActions.vue` puts the label in the button's
`aria-label` (line 10) and shows only the icon, which is `aria-hidden`;
so the label is the button's only name.

The key `userAccess.management.options` is defined in no locale file, in
any language: not in lib/pkp, not in OJS, OMP or OPS, not in their
plugins, and never was (no commit in lib/pkp's history adds it). The
browser's strings come from `UITranslator::getTranslationStrings()`,
which asks `Locale::get()` for every key listed in the app's
`registry/uiLocaleKeysBackend.json` (generated by the JavaScript build
from the `t()` calls); this key is listed there, and for a key with no
string `Locale::get()` answers the key wrapped in `##`, which becomes
the button's name.

The introducing commit itself used both keys. e65555cf gave the list's
actions column the header `t('common.moreActions')`, read by screen
readers only (`headerSrOnly`, then in `UserAccessManagerStore.js`, since
moved to `useUserAccessManagerConfig.js`), and gave the button in that
column the undefined key. Its pkp-lib side
([4729a3cd](https://github.com/pkp/pkp-lib/commit/4729a3cd9cabc98712aaf91a227d984bdce7dcb9))
created `locale/en/userAccess.po` with the list's other three keys but
not this one. The Invitations table on the same tab, built alongside,
got its twin `invitation.management.options` ("Invitation management
options").

Reach:

- Every row of the list, on every page and in every interface language:
  the one component draws them all. Seen in the browser on the first
  page of all three apps on `main` and 3.5; the later pages follow from
  the code.
- The key is used nowhere else in ui-library's `src`, lib/pkp or the
  apps; ui-library's Storybook mock strings (`public/globals.js`) carry
  an entry for it.
- The same mistake elsewhere, found by reading the code: ui-library on
  `main` uses five other keys that no `en` locale file of lib/pkp, the
  three apps or their plugins defines: `common.help` (the header's help
  link), `common.expand` (`VocabularyModal.vue`),
  `invitation.wizard.completeSteps` and `invitation.wizard.errors` (the
  invitation pages), `manager.category.delete.message` (the category
  delete dialog). Each needs its own text on its own screen, so they are
  left out of this fix.

## Proposed fix

Name the button with `common.moreActions`, the key its own column's
header already uses:

```diff
--- a/lib/ui-library/src/managers/UserAccessManager/UserAccessManagerCellActions.vue
+++ b/lib/ui-library/src/managers/UserAccessManager/UserAccessManagerCellActions.vue
@@ -2,7 +2,7 @@
 	<TableCell>
 		<DropdownActions
 			:actions="store.getItemActions({user})"
-			:label="t('userAccess.management.options')"
+			:label="t('common.moreActions')"
 			button-variant="ellipsis"
 			direction="left"
 			@action="(actionName) => store[actionName]({user})"
```

([fix.diff](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/issues/users-row-button-raw-code-name/fix.diff))

It follows how ui-library names these buttons: 18 other components with
an ellipsis `DropdownActions` (`FileManagerCellMoreActions`,
`DiscussionManagerCellActions`, `GalleyManagerCellActions`,
`MediaFileManagerCellActions`, …) pass `common.moreActions`, as does
this list's own actions column. The string exists in 34 of lib/pkp's 71
languages, so the button gets a real name at once in those, with no new
text for translators. `common.moreActions` is already listed in each
app's `uiLocaleKeysBackend.json`, so the fix needs nothing beyond the
build.

Tried on `main`, all three apps: all 25 row buttons on the first page
are named "More Actions", the focused one included. The menu's items
and the tab's other named controls (52 on OJS and OMP, 46 on OPS) read
the same with the fix in and out.

**Alternatives:**

- Add `userAccess.management.options` to lib/pkp's
  `locale/en/userAccess.po` ("User management options", like the
  Invitations table's): keeps the key, but every other language reads
  the code until its translators add the string, where "More Actions"
  is translated in 34 already.
- Name each button after its row ("Ramiro Vaca More Actions", as
  `ParticipantManager.vue` and `ReviewerSuggestionManager.vue` do;
  `pkp/pkp-lib#12646` suggests "Edit Emma"): tells a screen-reader user
  tabbing down the column whose menu each one opens. A wording choice
  for the team, which can sit on top of the fix.

**What goes with it:**

- Drop the `'userAccess.management.options'` entry from ui-library's
  `public/globals.js` (the Storybook mock strings) in the same change,
  since nothing uses the key after the fix.
- No stored data and no API change: only the button's accessible name
  changes.
- Backport: `stable-3_5_0` has the same file, and the diff applies as it
  stands.
- French (`fr_CA`) has no `common.moreActions` yet, so in French the
  button reads "##common.moreActions##" until its translators catch up.
- The guard: a check in ui-library's build that every key passed to
  `t()` has an `en` string in lib/pkp or the app, which would also
  catch the five keys above.

Small: one line in one ui-library component and one mock entry.
