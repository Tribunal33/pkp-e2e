# An invited newcomer is still greeted by their email address on a journal or press whose primary language is not the site's, when the manager works in the site's language

Intention gap. OJS, OMP and OPS at ojs `72b85f4ba0`, omp `3cd59e9443`,
ops `e2111e3aae` (lib/pkp `26ae6431b5` / `17a1f01fed`); the fix
pkp/pkp-lib#13397 (`aa077419e3`, 2026-09-26) for issue #13376 leaves this
case out. stable-3_5_0 shows it too since the backport (#13382,
`e4e720a7f6`) reached the three apps' pointers (lib/pkp `1fb843f491`,
driven on OJS and OMP 2026-10-01). Tracked in ci-triage "Open regressions" and the user-invitations
spec (U06 A10). Temporary: delete once acted on.

## Summary

Issue #13376 asks that the "Invite to a role" email greet a new user by
the given and family name the manager typed, not by their email address.
The fix does that on a journal or press whose primary language is the
site's. On one whose primary language differs from the site's (a French
journal on an English site), a manager working in English sends an email
that still reads "Dear <email address>," although names were typed in
both languages; the same manager working in French gets the name.

## Impact

Journal and press managers on multilingual sites whose journal's primary
language is not the site's, inviting a new user while their own
interface is in the site's language. The invitee gets a greeting by
address and a "To" line without a name: the very thing the issue asked to
fix, in a setup common for non-English journals on a shared site. No data
is lost and the invitation works. Minor: the wording of one email.

A related, narrower case: a name typed only in a journal's second
language (the form asks for the primary language's name) is also not
used.

## Steps to reproduce

Preconditions:
- A fresh install whose site primary language is English, with French
  (Canada) installed.
- A press (or journal) whose primary language is French (Canada), with
  English and French as its languages and form languages, and its Press
  Manager.

1. As the Press Manager, with the interface in English
   (`/<press>/en/management/settings/access`), open "Users & Roles",
   "Invite to a role".
2. Search for a new address, e.g. `newcomer@example.org`, and continue to
   "Enter details".
3. Fill in Given Name and Family Name in both languages (English "Eve" /
   "English", French "Eva" / "Anglais"), add the role Author, continue.
4. Send the invitation ("Invite user to the role").
5. Open the email the address received.

**Expected**: the email opens "Dear Eve English," (or the French name).

**Observed**: the email opens "Dear newcomer@example.org," and its "To"
line carries no name. The same steps with the interface in French give
"Dear Fanny Francais," on the same press; on a press whose primary
language is English, English names give "Dear Anna Smith,".

## Cause

`UserRoleAssignmentInvite::getMailableReceiver($locale)` now copies the
invitation's names onto the recipient, but only for `$locale`, the
language `getUsedLocale()` picks (the context's primary, here French).
The email's `{$recipientName}` is filled later by
`UserRoleAssignmentInvitationNotify::setData()` with
`$sendIdentity->getFullName()` and no language, which reads the request's
language (English) and falls back to the site's primary (English), where
the recipient has no name, and then uses `getEmail()`.

## Proposed fix

A proposal: copy every language the payload carries onto the recipient
(loop over `payload->givenName` / `familyName`), not only `$locale`; that
also covers a name typed only in a second language. Alternatively,
`setData()` could ask for the name in the locale the mailable was built
for. Either way the recipient's name should not depend on the language
the manager happens to work in.

## Evidence

- Kept check: `shared/playwright/checks/sync/pkp-lib-13376/greeting.js`,
  `RR_LEGS=a,b,s1,s2e,s2f` on OMP (the legs: English names, no name,
  French-only names, the French-primary press sent in English, the same
  sent in French); records `result-<app>.json`.
- Found by the regression read of #13397 (`.reports/sync/rr13376/suspicions.md`,
  S1 and S2, with an OJS control showing the same); held on a freshly reset
  OMP (`.reports/sync/s27hold-13376/`: a "Dear Anna Smith,", b the address,
  s1 the address, s2e the address, s2f "Dear Fanny Francais,").
- Before the change every newcomer was greeted by address (the old code
  tested properties that never existed), so this is not a regression;
  it is the part of the issue the fix does not reach.
- Also seen, not part of this report: a typed name is put into the HTML
  email unescaped ("Zoe <Ann>" reads "Dear Zoe  Smith & Co,"), a
  pre-existing line the fix now feeds with typed names (rr13376 S3).
- Not driven: OPS (the same lib/pkp code). The 3.5 backport driven
  2026-10-01 on OJS and OMP at lib/pkp `1fb843f491` (the same script,
  `PKP_E2E_LINE=stable-3_5_0`; `.reports/sync-3_5/s01-13376/`): leg
  `s2e` greets by the address, as on `main`.
