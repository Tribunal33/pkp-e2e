# A users import now fails on an empty start date, and adds a future-dated role again on every re-import

Regression. OJS and OMP at ojs `9d9f116f38`, omp `480045c32` (lib/pkp
`fab29cfeca`); introduced by pkp/pkp-lib#13390 (`85f6b3c074` "Fix
reviewer role check and start date in user import/export", merged
2026-09-28). stable-3_5_0: shows it too at lib/pkp `8809a197de` (the same
patch). Tracked in ci-triage "Open regressions" and the import & export
spec (U63 A18, A17). Temporary: delete once acted on.

## Summary

The Users XML import now keeps the start date a users file gives each
role, as intended (before, every role started on the import day). Two
files that imported before no longer do what they did: a role whose
`<date_start>` is empty makes the import fail on the server (the account
is created without its role, the users after it in the file are not
imported, and the results tab stays blank), and a role
whose start date is in the future is added again each time the same file
is imported, so the user ends up holding it two, three or more times.

## Finding 1 — An empty `<date_start>` fails the import on the server

### Impact

Journal and press managers who import users from a file written by
another tool or by hand, where a role's start date is present but empty
(the file format allows it). The import answers with a server error, the
"Results" tab opens blank, the user is created without the role the file
gave, and every user after it in the file is left out. The manager has
to find what was and was not imported and finish by hand; nothing says
the import went wrong. A start date that is not a date (such as "soon")
fails the same way. Minor: an unusual file, but the failure is silent
and half-done.

### Steps to reproduce

Preconditions:
- A fresh OJS install with its test journal and its Journal Manager.
- A users file (below) naming a new user with the role "Section editor"
  and an empty start date.

```xml
<user_user_group>
  <user_group_ref>Section editor</user_group_ref>
  <date_start></date_start>
  <masthead>true</masthead>
</user_user_group>
```

1. As the Journal Manager open Tools › "Import/Export" › "Users XML
   Plugin".
2. On "Import Users", upload the file and press "Import".

**Expected**: "The import completed successfully. …", the user listed
with the role "Section editor" starting today (as before the change).

**Observed**: the request answers 500 with an empty body and the
"Results" tab opens blank. Settings › Users & Roles › "Users" lists the
new account with no role in the journal (the account signs in), and a
second user listed after it in the same file is not imported. The
server log reads:

```
SQLSTATE[22007]: Invalid datetime format: 7 ERROR:  invalid input syntax for type timestamp: ""
SQL: insert into "user_user_groups" ("user_id", "user_group_id", "date_start", "date_end", "masthead") values (53, 59, , ?, 1)
```

The same file with no `<date_start>` element imports, the role starting
today. A start date of "soon" fails the same way (`Carbon\Exceptions\InvalidFormatException:
Could not parse 'soon'`); an empty `<date_end>` failed like this before
the change too.

### Cause

`UserXmlPKPUserFilter` reads `$dateStart = $dateStartNode?->textContent`,
which is `""` for an empty element, and the new `$dateStart ??=
Core::getCurrentDate();` only replaces `null`, so `""` goes into the
`date_start` timestamp column. Before, the line read an undefined
`$startDate` and always took today.

### Proposed fix

A proposal: treat an empty value like a missing one
(`$dateStart = $dateStartNode?->textContent ?: null;`, the same for
`$dateEnd`). A date the database cannot parse would still fail the same
way; validating it with Carbon and falling back to today, or reporting it
in the import's warnings, covers that too.

## Finding 2 — A role with a future start date is added again on every import of the same file

### Impact

Managers who import the same users file twice (a retry after a partial
failure, or a periodic sync from another system) where a role starts on
a future date. Each import adds another copy of the role: Users & Roles
lists "Section editor" two, three times with the same start date, and
each copy must be removed by hand. Minor: duplicate rows, no loss.

### Steps to reproduce

Preconditions:
- A fresh OJS install with its test journal and its Journal Manager.
- A users file naming a new user with the role "Section editor" and
  `<date_start>2027-06-01 00:00:00</date_start>`, no `<date_end>`.

1. As the Journal Manager open Tools › "Import/Export" › "Users XML
   Plugin", upload the file on "Import Users" and press "Import".
2. Import the same file again, then a third time.
3. Open Settings › Users & Roles › "Users" and find the user.

**Expected**: each import reads "The import completed successfully. …";
the user holds "Section editor" once.

**Observed**: each import reads "The import completed successfully. …";
the user's row lists "Section editor / Section editor / Section editor"
and "2027-06-01" three times (three identical role rows). The same file
with a past start date (`2020-01-01`) imported twice leaves one role.
The same happens on OMP with "Series editor".

### Cause

Before importing a role the filter checks whether the user already holds
it: `withActive()` (started, not ended) for a role without an end date,
`withEnded()` for one with. A role that starts in the future is neither,
so the check never finds the row the previous import wrote. Before the
change every imported role started today and was active at once, so the
second import skipped it.

### Proposed fix

A proposal: for a role without an end date, look for any row of that user
group without an end date (active or starting later, e.g.
`withActiveAndActiveInFuture()`, which `UserGridHandler` already uses),
or for a row with the same start date.
