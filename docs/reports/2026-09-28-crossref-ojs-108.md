# When Crossref cannot give an article's citations, "View citing articles" does nothing and the article page throws a script error

Defect. OJS at the PR heads of dev-team#316 before their merge: ojs
`3c9d06844f` (ojs#5810), lib/pkp `fec909fbfd` (pkp-lib#13292),
lib/ui-library `67f0ea20` (ui-library#992), plugins/generic/crossref
`0dd599a` (crossref-ojs#108); introduced by crossref-ojs#108's Cited-by
store, on a ui-library bug present on `main` since `9e613aad`
(ui-library#702). stable-3_5_0: the feature is not there, not driven.
Tracked in ci-triage "Companion branches" (`i13221-main`). Temporary:
delete once acted on.

## Summary

With Cited-by on, an article whose citations Crossref will not give
(wrong or expired credentials, Crossref down or unreachable) shows
"This article has been cited -- times according to Crossref" and a "View
citing articles" button that does nothing when pressed: no window, no
message. The page's own script fails in the browser ("l is not a
function") each time the citations are requested.

## Impact

Every reader of every article with a DOI in a journal whose Crossref
credentials are wrong, or while Crossref is unreachable, meets a button
that looks broken. The journal's staff get no sign that the credentials
are the cause (the reason is in the server log only). No data is lost.
Each such page view also asks Crossref twice, because the 502 answer is
retried by the browser's fetch helper and failures are not cached.
Minor: nothing breaks beyond the block, but it is the state a new
journal's misconfiguration produces first.

## Steps to reproduce

Preconditions:
- OJS at the PR heads above, the Crossref Manager Plugin enabled for a
  journal, DOIs on with a prefix, one published article with a DOI.
- On Settings › Distribution › DOIs › Registration: "Crossref" chosen,
  "Enable Cited-by" ticked, a made-up Username and Password, saved.

1. Signed out, open the article's page (`/<journal>/article/view/<id>`).
2. Wait for the "Cited by" block in the side column.
3. Press "View citing articles".

**Expected**: a window titled "Articles that cite this article
(Crossref)" saying the citations could not be retrieved (or no button
while the count is unavailable).

**Observed**: the block reads "This article has been cited -- times
according to Crossref"; pressing "View citing articles" opens nothing.
The browser console shows, on page load:

```
GET /index.php/<journal>/api/v1/crossref/citedBy/<id>  502  (twice)
{"error":"An error occurred while retrieving Crossref citations for this article."}
TypeError: l is not a function
    at h (js/build_frontend.js)
    at async loadCitations (plugins/generic/crossref/public/build/crossref.js)
```

Control: the same article with citations available (a cached answer)
shows "3 times" and the window lists them; "Copy Citation Details" works.

## Cause

Two things meet. In ui-library `main`, the frontend
`src/frontend/composables/usePkpFetch.js` calls
`usePkpModal().openModalNetworkError(e)` for any error other than a
400/422 it was told to expect, but the frontend
`src/frontend/composables/usePkpModal.js` exposes that function as
`openDialogNetworkError`; the call throws `TypeError`, so `fetch()`
rejects instead of returning with `isSuccess` false. In
crossref-ojs#108, `useCrossrefCitedByStore.js` `loadCitations()` awaits
`fetch()` without a `try`, so the rejection skips `hasError = true` and
`isLoading = false` (the count stays "--" by accident), and
`openCitedByModal()` awaits the same rejected `loadPromise`, so
`openDialog()` is never reached. The 502 the controller answers is in
ofetch's default retry list, hence the second request.

## Proposed fix

- crossref-ojs#108: in `loadCitations()`, wrap `await fetch()` in
  `try … catch` and set `hasError`; in `openCitedByModal()`, open the
  window even after a failure and let `CrossrefCitedByModal.vue` say the
  citations could not be retrieved (today it would say "0 citations"),
  or hide "View citing articles" while `hasError`. Consider `retry: 0`
  for this request, or answering the Crossref failure with a status
  ofetch does not retry.
- ui-library (separately, it affects every frontend fetch, the reader
  comments included): call `openDialogNetworkError` in the frontend
  `usePkpFetch`, and decide whether a reader should see that dialog for a
  background request like this one.
