# After an upgrade that keeps an old configuration file, the dashboard's submission search fails for every editor

- **Severity** medium
- **Effort** small
- **Kind** regression
- **Crash** server
- **Affects**
  - main: OJS, OMP, OPS
  - 3.5: none (walked on OJS; OMP, OPS by code)
  - 3.4: none (code; a missing line reads as Off)
  - 3.3: none (code; 3.3 has no strict mode)
- **Introduced** `pkp/pkp-lib#12016` for `pkp/pkp-lib#11583` · [cb32f21f94](https://github.com/pkp/pkp-lib/commit/cb32f21f942cdef34bd6c817b42a83986b4b369e) · 2026-01-06 · Touhidur Rahman (touhidurabir)
- **Upstream** none found (2026-10-05)
- **Tracked in** ci-triage "Open regressions"; the strict-mode symptoms themselves are spec U23 [A17](https://github.com/jardakotesovec/pkp-e2e/blob/main/docs/specs/U23-submissions-dashboard.md#a17) (the search) and U39 [A5](https://github.com/jardakotesovec/pkp-e2e/blob/main/docs/specs/U39-submission-and-publisher-libraries.md#a5) (issue report [pkp-e2e#698](https://github.com/jardakotesovec/pkp-e2e/issues/698), which left this default open) · Temporary: delete once acted on
- **Checked** 2026-10-05, each branch's tip (the commits in Evidence)

## Summary

On `main`, an install whose configuration file has no "strict" line now
runs in strict mode, a developer setting that 3.5 and 3.4 leave Off when
the line is missing. Configuration files written for 3.3 or earlier
have no such line, so a journal, press or server that upgrades and
keeps its configuration file, as the upgrade instructions say, ends up
in strict mode without anyone turning it on. Strict mode then breaks
every search in the dashboard's "Search submissions" box: the app fails
on the server and the list reads "Search Results (0)". It also breaks
the other screens the U39 A5 report lists, and any third-party plugin
that still uses the old global names.

## Impact

- **Lost**: nothing is stored wrong; editors cannot find submissions by
  search, and the error log fills with "Missing locale key" lines.
  Nobody is told why.
- **Who**: every editor and manager on an install upgraded from 3.3 or
  earlier that kept its configuration file. Many sites upgrade this way,
  because 3.3 was the long-term release for years. A new install is not
  affected, because the 3.4 and later template writes `strict = Off`.
- **Way round**: add `strict = Off` under `[general]` in
  `config.inc.php`. Nothing on screen points to it.

Medium: a secondary task fails for everyone, but only on upgraded sites
whose configuration file predates 3.4, and one configuration line
restores it. It would be high if most sites upgrading to the next
release came from 3.3 with their old file.

## Steps to reproduce

Preconditions:
- The default dataset, OJS `main` (the same on OMP and OPS).
- In the install's `config.inc.php`, under `[general]`, delete the line
  `strict = Off`, as a 3.3 configuration file would be.

1. Sign in as `dbarnes`.
2. On the dashboard, type "cashmere" into the "Search submissions" box
   in the side menu and press Enter.

**Expected**: "Search Results (1)", listing "2 Corino — The influence of
lactation on the quantity and quality of cashmere production", as with
`strict = Off` and as on 3.5 with the line missing.

**Observed**: "Search Results (0)" and "No Items". The list's request
fails:

```
GET /index.php/publicknowledge/api/v1/_submissions?searchPhrase=cashmere&…  → 500
{"error":"Undefined constant \"PKP\\submission\\ASSOC_TYPE_PUBLICATION\""}
```

The server log reads `production.ERROR: Undefined constant
"PKP\submission\ASSOC_TYPE_PUBLICATION" … at
lib/pkp/classes/submission/Collector.php:692`. The same happens on OMP
(searching "Imagined" for "The West and Beyond: New Perspectives on an
Imagined Region") and on OPS ("cashmere"). With the line back the search
works. On the same install, the reviewer `jjanssen`'s step 3 "Reviewer
Files" list stays on "Loading", as the U39 A5 report describes for
`strict = On`.

## Cause

`PKPContainer::__construct()` sets the application's strict mode from
`Config::getVar('general', 'strict', true)`, so a configuration file
without the key gives `true`. That default came with cb32f21f94
(`pkp/pkp-lib#12016`), which replaced the `PKP_STRICT_MODE` constant,
defined in `PKPApplication::__construct()` as `(bool)
Config::getVar('general', 'strict')`, where a missing key was Off. The
change was for `pkp/pkp-lib#11583`, whose discussion is about the
PHPUnit runs: strict mode in unit tests and the missing-locale-key log
lines. The same commit already forces strict mode for those runs
(`PKP_PHPUNIT_STRICT_MODE`, set in `tests/phpunit-bootstrap.php`), and
nothing in the issue asks for a production install with no line to run
strict. 3.5 (`stable-3_5_0` `PKPApplication.php:167`) and 3.4 still read
a missing line as Off.

What strict mode does on `main`, checked in the code:
- `PKPApplication::__construct()` and each app's `Application` skip
  `registerGlobalConstants()`, so the global `ASSOC_TYPE_*`, `WORKFLOW_*`
  and similar aliases do not exist (and `MetadataTypeDescription` skips
  `ASSOC_TYPE_ANY`). Code that still reads a bare global fails with
  "Undefined constant": `Submission\Collector` line 692 (the dashboard
  search, walked on all three apps; its bare constant came with pkp-lib
  0789f18150, `main` only, U23 A17) and the two places the U39 A5 report
  names (the Submission Library's "Delete" and the reviewer's file list).
  So does any third-party plugin written against the aliases 3.3 and 3.4
  offered.
- `Locale::get()` writes every missing locale key to the error log
  (`Locale.php:519`), on every request that meets one.

The configuration templates: `stable-3_3_0`'s has no `strict` line;
`stable-3_4_0`, `stable-3_5_0` and `main` ship `strict = Off`.

## Proposed fix

A proposal: read a missing line as Off again, keeping the forced strict
mode of the unit tests:

```diff
--- a/lib/pkp/classes/core/PKPContainer.php
+++ b/lib/pkp/classes/core/PKPContainer.php
@@ -78,7 +78,7 @@ class PKPContainer extends Container
             // This takes precedence over config settings
             defined('PKP_PHPUNIT_STRICT_MODE') && PKP_PHPUNIT_STRICT_MODE === true
                 ? true
-                : Config::getVar('general', 'strict', true)
+                : Config::getVar('general', 'strict', false)
         );
     }
```

([fix.diff](../../shared/playwright/checks/sync/pkp-lib-12016/fix.diff))
This restores what 3.5 and 3.4 do and what the template's `strict = Off`
says. The developers' own setting, `strict = On`, keeps working, and so
do the unit tests. Tried on OJS `main`: with the line missing, the
search lists the submission; with `strict = On` it still fails as
before, so the setting itself is untouched.

Alternatives: fixing the bare constants alone (the U39 A5 report's fix)
is needed in any case. It clears the three known screens, but leaves the
log noise and third-party plugins to break on upgraded sites. Adding the
line during the upgrade is not possible, because the upgrader does not
write the configuration file. A release note that tells upgraders to add
the line would reach only those who read it.

Guard: a unit test that boots the container with a configuration lacking
`strict` and expects `getApplicationStrictModeStatus()` to be false
outside PHPUnit's forced mode.

Small: one word in one shared file, and a unit test.
