# A users file the Users XML Plugin cannot read ends in a blank "Results" tab, with no reason given

- **Severity** medium
- **Effort** small
- **Kind** regression
- **Crash** server
- **Affects**
  - main: OJS, OMP (OPS has no Users XML Plugin)
  - 3.5: OJS, OMP
  - 3.4: OJS, OMP (code)
  - 3.3: none (code; the tab lists the validation errors)
- **Introduced** `pkp/pkp-lib#6960` for `pkp/pkp-lib#6490` · [049f5f85f3](https://github.com/pkp/pkp-lib/commit/049f5f85f34c602d0feeabd7e5de72ad00a095a5) · 2021-04-19 · Dimitris Efstathiou (defstat)
- **Upstream** `pkp/pkp-lib#11628` (open): the same blank tab and server error, reported on OJS 3.5.0 for a file with no user groups; no fix linked
- **Tracked in** spec U63 [A13](https://github.com/jardakotesovec/pkp-e2e/blob/main/docs/specs/U63-import-export.md#a13)
- **Checked** 2026-09-30, each branch's tip (the commits in Evidence)

## Summary

A journal or press manager imports a users file in Tools › "Users XML
Plugin", and the file does not match the format the tool reads: a user
with no password, a user's role entry without its masthead setting, an
unknown element, another kind of document, or a file that is not XML.
The tool should refuse the file and tell the manager why. Instead the
server answers the import with an error, and the "Results" tab that the
import opens stays blank: no text, no message. No account is created.

The manager cannot find out on screen what is wrong with the file, and
the blank tab can pass for an import still running. A users file
exported from 3.4 is refused this way on 3.5 and later, because the
file format changed in 3.5.

## Impact

- **Lost:** the import and the manager's time. The reason exists only
  in the server log.
- **Who:** a journal or press manager who imports a users file that the
  tool refuses: a file edited or generated by hand, or a file exported
  from a 3.4 install.
- **Way round:** none on screen. The manager has to guess what is wrong
  with the file, or ask whoever can read the server log.

Medium: the import fails with no reason on screen, and nothing already
stored is harmed. A 3.4 export fails too, but its refusal is the format
change that the 3.5 release notebook lists, and that file would not
import even with this fault fixed. What this fault takes away is the
reason. It would be high if files in the version's own format were
refused.

## Cause

The users import does not catch the exception the filter throws for
input it refuses. In lib/pkp
`plugins/importexport/users/PKPUserImportExportPlugin.php`,
`display()` case `import` (lines 133–160) calls `importUsers()`, which
runs the `user-xml=>user` filter, `UserXmlPKPUserFilter`. After the
filter returns, the case reads `libxml_get_errors()` into
`validationErrors`. The app's own template,
`plugins/importexport/users/templates/results.tpl` (the same in OJS and
OMP), shows those errors first, under "Validation errors:"
(`plugins.importexport.common.validationErrors`).

The filter never returns for a file that fails the schema.
`Filter::execute()` (lib/pkp `classes/filter/Filter.php`, lines
445–454) checks the input with `supportsAsInput()`.
`XMLTypeDescription::checkType()` validates the file against
`pkp-users.xsd` and writes the libxml errors to the server log. When the
check fails, `execute()` throws
`Exception(__('filter.input.error.notSupported'))`. Nothing in
`display()` catches it, so the request fails with 500, and the libxml
errors that explain the refusal are never shown.

This worked before. The users import has shown libxml errors under
"Validation errors:" since `pkp/pkp-lib#1347`
([789936aff0](https://github.com/pkp/pkp-lib/commit/789936aff0205ce70cfd9e17bfaeeae20321cfbf), 2016).
At that time `Filter::execute()` returned null for unsupported input,
so `display()` went on to the template. The commit named under
Introduced, part of the Native XML import/export rework, made
`execute()` throw instead. It put the Native XML import inside
`PKPImportExportDeployment::import()`, which catches `Error | Exception`,
records the message and keeps the libxml errors for the results page.
The same commit added three stubs to the Users XML plugin
(`getImportFilter()`, `getExportFilter()` and
`getAppSpecificDeployment()`, each throwing `BadMethodCallException`).
It did not change the plugin's import path, which does not go through
`PKPImportExportDeployment::import()`.

Reach:

- Every file that fails `pkp-users.xsd`, such as the five in the Steps
  (walked).
- A file exported from 3.4 (code, and the schema check in Evidence).
  3.4's "Export Users" writes each role as `<user_group_ref>` directly
  under `<user>`, writes `<show_title>` in `<user_group>`, and writes no
  `<masthead>`. 3.5 refuses such a file for the missing `<masthead>` and
  the unwrapped `<user_group_ref>`. `main` refuses it for
  `<show_title>` and the unwrapped `<user_group_ref>`. Both end in the
  blank tab. The format change is `pkp/pkp-lib#11479`, which the 3.5
  release notebook lists under "Import/Export".
- Exceptions the filter throws after the schema check also leave
  `display()` uncaught and give the same blank tab. Examples are "User
  given name is empty." in `UserXmlPKPUserFilter::parseUser()`, and
  "Unacceptable role_id" in `NativeXmlUserGroupFilter` for a new group
  (code). The import is not one transaction: the users before such an
  exception in the file stay created, and each has already been sent
  its "User Created" email (code).
- OJS's command-line import (`UserImportExportPlugin::executeCLI()`)
  calls `importUsers()` without a catch too. It prints the exception
  rather than failing silently. OMP has no command-line users import:
  its `executeCLI()` throws `BadMethodCallException` (code).
- The Native XML Plugin's import goes through
  `PKPImportExportDeployment::import()` and is not affected (code).

## Proposed fix

A proposal, tried on `main`
([fix.diff](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/issues/users-import-unreadable-file-empty-results/fix.diff)).

Recommended: catch the import's failure in `display()` case `import`,
as `PKPImportExportDeployment::import()` does, and let the results
template show it:

```diff
+use Error;
 use Exception;
 …
                 $filter = $this->getUserImportExportFilter($context, $user);
-                $users = $this->importUsers(file_get_contents($temporaryFilePath), $context, $user, $filter);
+                try {
+                    $users = $this->importUsers(file_get_contents($temporaryFilePath), $context, $user, $filter);
+                } catch (Error|Exception $e) {
+                    // A file the schema refuses leaves its reasons in libxml_get_errors(), shown below
+                    // under "Validation errors:"; any other failure is shown as the filter's own error.
+                    $users = [];
+                    $filter->addError($e->getMessage());
+                }
```

`display()` is the one screen caller, and it already turns the libxml
errors and the filter's errors into the results. So the fix needs no
new string and no template change.

What the tab says with the fix:

- A file that fails the schema imports nothing. The tab shows
  "Validation errors:" with libxml's lines in place of the success
  sentence, as in 3.3. It does not say in a separate sentence that
  nothing was imported.
- After an exception further into the file, the tab shows the
  exception's message under "Import/Export errors:". The accounts
  created before it stay, and the tab does not list them. It does not
  list imported accounts after a problem today either, and `results.tpl`
  never shows `$users`, so `$users = []` hides nothing.

Tried on OJS and OMP. With the fix, each of the five files answered 200,
and the tab showed "Validation errors:" with the reason. For the first
file that was "Element '{http://pkp.sfu.ca}user_user_group': Missing
child element(s). Expected is one of ( {http://pkp.sfu.ca}date_start,
{http://pkp.sfu.ca}date_end, {http://pkp.sfu.ca}masthead )." No account
was created. Two files the tool reads today gave the same result with
and without the fix:

- The control file imported as above.
- A users file whose user has the username `dbarnes` and a new email
  address showed "Import/Export errors:" with "The username "dbarnes"
  and the e-mail "u63a13x@mailinator.com" do not match to the one and
  the same existing user.". `dbarnes` was left unchanged.

**Alternatives:**

- Add a sentence saying that nothing was imported, such as the Native
  XML import's "The process failed. Check below for errors/warnings."
  (`plugins.importexport.native.processFailed`). It belongs in the
  "Validation errors:" branch only, since the "Import/Export errors:"
  branch also follows imports that partly succeeded. It is a template
  change in both OJS and OMP, on top of this fix.
- Run the users import through `PKPImportExportDeployment::import()`,
  as the Native XML plugin does, so that a failure part way through
  undoes the whole file. This is larger. The users template reads the
  filter's errors, not the deployment's. A rollback also needs a
  decision about the "User Created" emails already sent for the
  accounts it would undo.
- Make `Filter::execute()` return null again. That would hide the
  failure from the Native XML import and from every other caller that
  relies on the exception.
- Catch inside `importUsers()`. That would also change OJS's
  command-line import, which today at least prints the exception.

**What goes with it:**

- No stored data, API or hook changes.
- libxml's wording is sometimes indirect. For a user with no
  `<password>` it names the next element: "Element
  '{http://pkp.sfu.ca}date_registered': This element is not expected.
  …". The fix shows it as it is.
- Backport: the diff applies unchanged to `stable-3_5_0` (the same
  file) and to pkp-lib `stable-3_4_0` (a patch dry run).
- Guard: an e2e scenario in U63 that imports a file which fails the
  schema, and checks for "Validation errors:" and that no account was
  created.

Small: a few lines in one pkp-lib method, tried on both apps.
